# desktop

The Pets-Driven app itself: a Tauri (Rust) shell hosting a React frontend, the always-on-top pet windows, and the ingress that turns coding-agent hook events into pet reactions. See the repo-root `CONTEXT.md` for the domain language and `ARCHITECTURE.md` for the end-to-end event flow.

## Commands

```bash
pnpm dev                                      # tauri dev (from the repo root)
pnpm --filter pets-driven dev:tauri           # frontend only, on the Tauri dev port
pnpm dev:playground                           # simulation playground in a browser
pnpm --filter pets-driven test                # vitest run
pnpm --filter pets-driven typecheck           # tsc
pnpm test:e2e                                 # playwright test
```

`README.md` in this directory documents the development fixtures (`?fixture=<id>`) and the pet-window surface fixtures — read it before hand-building state to reproduce a screen.

## Layout

- `src/app/` — the main window UI; `src/app-state/` holds adoption, card status, and surface state
- `src/pet-window/` — the overlay surface: transport, layout, projection, sprite, hit region, fixtures, and the single-window overlay (`pet-overlay-*`)
- `src/adapters/agent-events/` — keeps each provider's raw hook contract behind its own adapter and emits the app-owned `AgentEvent` interface
- `src/playground/` — simulation playground; entry points are `main.tsx` and `playground-main.tsx` beside them
- `src-tauri/src/` — Rust: `claude_hook_ingress.rs`, `state_store.rs`, `pet_windows.rs`, `terminal_channel.rs`, `embedded_terminal.rs`, `pet_assets.rs`, `claude_plugin.rs`, `codex_plugin.rs`
- `tests/` — vitest; `e2e/` — Playwright
- `public/codex-pets/` — generated by `pnpm sync-pets`, git-ignored

## Cross-module dependencies

- Consumes `@pets-driven/pet-engine` (simulation), `@pets-driven/design-system` (tokens and components), `@pets-driven/i18n` (`desktop` namespace).
- Receives agent events from `plugins/pets-driven` hooks over local HTTP; the Rust ingress is the boundary.
- Pet assets come from the repo-root `pets/` directory via `pnpm sync-pets`.
- Nothing depends on this app — it is a leaf consumer, so behavior changes that belong to every surface go in the engine or the design system instead.

## Non-obvious rules

- **Note: there are two window modes, and they part company only at the last hop.** By default a pet owns a small always-on-top window that the shell moves natively; in single-window overlay mode (Settings → Pet windows, stored in localStorage) one transparent click-through window covers the desktop and every pet is an element inside it. The world, the projection and `PetWindowView` are shared — what differs is that the overlay gets the whole roster in one `PET_OVERLAY_FRAME_EVENT` per tick with positions in it, instead of a native placement batch plus a per-pet frame event. `PetSurfaceHost` (`src/pet-window/pet-surface-host.ts`) is the seam: a pet states its intent (resize me, drag me, hand the mouse back) and whoever owns the window carries it out or absorbs it.
- **Gotcha: the single-window overlay may only take the mouse where a pet actually is, and it cannot work that out itself.** It covers the whole desktop, so while it is not click-through it swallows every click meant for whatever is underneath — and while it *is* click-through the webview is never told the cursor moved, so nothing inside it can notice a pet being approached. The host decides instead, from the cursor it already polls: `isPetOverlayInteractive` arms on the exact pet rects and releases only once the cursor is clear of them by a margin, and a drag or resize holds it with `surface.capture.start` / `surface.capture.end` (which expire, so a missed release cannot strand a desktop-wide window in the mouse's way). Inside the window, hit shims — not the pet's whole frame — take the pointer, so the pet in front does not swallow clicks aimed at the pet behind it through its transparent margin.
- **A trinket overlay is not a pet window.** World items get their own tiny click-through windows (`sync_item_windows` in `pet_windows.rs`, `src/pet-window/item-window-route.tsx`), and unlike a pet they carry no frame stream: a trinket never moves once it lands and stops existing the moment a pet takes it, so the host reconciles the whole set in one shell call and the window renders straight from its URL. They share `pet-window.html`, which is why the pet surface is behind a dynamic import — a trinket must not parse the sprite atlas to draw one glyph.
- **A borrowed ability counts down in whole seconds because the frame stream charges by the change.** The trinket badge in the status card (`pet-window-status.tsx`) is fed from `carryingFromPet`, which converts the engine's `CarriedItem.expiresAt` against `snapshot.now` into `remainingSeconds` / `totalSeconds` — a per-tick float would repaint every carrier's webview sixty times a second for a number no one reads at that resolution, so the bar is eased across each one-second step in CSS instead. Anything else added to `PetWindowFrameSprite` has the same cost, and must be appended *last*: `isSamePetWindowPresentation` compares serialized sprites, so `use-pet-window-surface.ts` rebuilds the previous sprite in the same key order and normalizes every optional field, or a pet re-renders each tick on being different from itself.
- **The pet window renders, it does not simulate.** It is a separate 192x268 always-on-top window driven entirely by frame events from the main window. Wrong-looking output is usually projection, not simulation — check `src/pet-window/pet-window-projection.ts` and `src/pet-window/pet-window-layout.ts` first.
- **A pet facing the wrong way while it walks is the pet's own `swapRunningDirections`, not a projection bug.** Spritesheets found online often draw the two running rows the opposite way round from the atlas; the edit screen's checkbox sets a persisted per-pet flag that the projection feeds to `resolveRunningDirection`, which trades the two rows. Nothing is mirrored — the engine's row-only rule still holds — and no system reads the flag, so it stays out of the simulation.
- **The note is the only line the pet window says on its own.** Everything else in the status card is projected: the engine owns the single message line through the agent channel, and the window just renders it. A pet's note is host state, not simulation state, so it rides the frame stream beside the name and folder and `use-pet-window-note.ts` decides when it is said — immediately when it changes (the only feedback a save from the context menu ever gets) and on a long idle cadence, both gated on the pet having no agent-channel line of its own. Nothing about the note reaches the engine; adding note-driven *behavior* would be an engine change, not another timer here.
- **Gotcha: an overlay window's transparency cannot wait for React.** Each surface adds its own `*-document` class on mount, but the shell shows the window as soon as the simulation places it — ahead of the lazy surface chunk — and the design-system base paints the body opaque until then, which is a white square flashing where the pet is about to stand. `pet-window.html` and the top of `styles/pet-window.css` claim `background: transparent` unclassed for that gap; the classes still carry the per-surface sizing and the fixture backdrops.
- **Gotcha: the OS window never shrinks to fit a small pet.** The projection must center the fixed window rather than the scaled frame, and every vertical term must be scaled, or small pets sink and the collision capsule clips.
- **Note: the pet-window routing suite has a known flaky case** — the "resets the adopted pet simulation" case in the `tests/pet-window/` routing suite fails intermittently on unrelated changes. Confirm it fails on a clean tree before blaming your diff.
- **Provider hook payloads never enter the engine directly.** The Rust ingress emits a provider envelope, `claude-hook-adapter.ts` and `codex-hook-adapter.ts` parse their own contracts, and both target the app-owned `AgentEvent` interface. Adding a provider means adding an adapter, not widening another provider's payload type.
- **Hook events are not all lifecycle events.** Tool hooks map to a `tool.used` pulse, not `task.started`: they fire many times per task. Raw tool names stop at the adapter boundary; an optional study/edit/run activity may bias the next behavior, but it never becomes speech or a direct animation command.
- **Gotcha: `PostToolUseFailure` is deliberately not registered in `hooks.json`.** It fires on ordinary tool failures (a grep that matches nothing, a rejected edit), and `task.failed` is terminal — a tool pulse no longer reopens it. Registering it would freeze the pet on the first failed grep until the user pets it. `StopFailure` is the turn-level failure and is the one that is registered.
- **Note: `forward-codex` falls back to the legacy `/claude-hook` route** when `/codex-hook` is unavailable (an app predating that route). The ingress tags anything on that path `provider: "claude"`, so a Codex payload is then parsed by the Claude adapter — it resolves because both read `session_id`, but a payload carrying only `thread_id` would lose its source identity.
- **The app types a command into the terminal; the user presses Enter.** `EmbeddedTerminal`'s `prefill` waits for the session's first byte of output (the prompt) and then goes through `term.paste()` — never a stdin write with a trailing `\r`. Sending early lands in a half-painted prompt, and a command the user cannot read is one they cannot review, which matters because the only caller installs software behind an npx confirmation prompt. `onRunningChange` reports when closing has become destructive — true on the `\r` that hands the line to the shell, false when the command is done — and like any callback prop here it must stay out of the effect's deps, or the PTY restarts on every render of the parent.
- **Whether the shell is idle is an OS question, not an output-stream question.** A shell prints its prompt with the same bytes it prints everything else, so `terminal_is_busy` asks the OS instead: the tty's foreground process group on Unix, a live child of the shell on Windows (ConPTY has no foreground group, and its host process is parented to the app, not the shell). It answers "idle" whenever it cannot tell — an unknown session, no pid, a failed snapshot — because the caller uses a "busy" to guard a destructive close, and a spurious guard only costs a confirmation.
- **Fixture state is development-only and in-memory.** It is served only from a loopback host and never reads or overwrites persisted Tauri state, so it is safe to explore but useless for reproducing a persistence bug.
- **Rust and TypeScript state must move together.** `state_store.rs` owns persisted state; a new persisted field needs the Rust side, the adapter, and the app-state module updated in the same change.
